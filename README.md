# Job Research

پایهٔ برنامهٔ جستجوی شغل برای نقش‌های فنی Senior DevOps، Platform و SRE با هدف ریلوکیشن.

## وضعیت فعلی

این نسخه اتصال قابل تنظیم به مدل، وایت‌لیست منابع، فیلتر اولیه، ارکستریتور،
ثبت وضعیت در SQLite و تولید پیش‌نویس از ورودی JSON را پیاده می‌کند.
جستجوی اینترنتی و جمع‌آوری اولیه با Brave اضافه شده است؛ کلید سرویس لازم است.
ارسال یک پیش‌نویس تأییدشده با SMTP، جستجوی دوره‌ای و اعلان تلگرام اضافه شده‌اند.
اتصال خودکار کل مسیر جستجو تا ارسال هنوز پیاده نشده است.
هیچ رزومه یا اطلاعات محرمانه‌ای در مخزن قرار ندارد.

## اجرا

Python 3.10+؛ برای خواندن PDF وابستگی pypdf را نصب کنید.

```bash
cp .env.example .env
python -m pip install -r requirements.txt
# Place your final text PDF here as resume.pdf
python model_client.py --job data/job.txt
```

پوشهٔ data را بسازید؛ job.txt متن آگهی باشد. متن رزومه از resume.pdf خوانده می‌شود؛
برای استفاده از پروفایل JSON قبلی، --profile data/profile.json را بدهید. خروجی، JSON دارای subject و body است و ایمیلی ارسال نمی‌شود.

## اتصال به مدل

LLM_BASE_URL آدرس پایهٔ سرویس شامل مسیر /v1 است؛ IP، پورت و مسیر
همگی قابل تغییرند. LLM_MODEL نام دقیق مدل ارائه‌شده در سرویس است.
LLM_API_KEY برای سرویس‌هایی که احراز هویت دارند تنظیم می‌شود.

برای vLLM آدرس سرویس خودتان را وارد کنید.
برای OpenRouter آدرس پایه https://openrouter.ai/api/v1 است؛ کلید و شناسهٔ
مدل باید متعلق به همان سرویس باشند. برای سایر سرویس‌ها نیز API سازگار
با Chat Completions لازم است. تغییر سرویس صرفاً با تغییر تنظیمات انجام می‌شود.
سرویس‌های دارای پروتکل متفاوت به adapter جدا نیاز دارند.

خطا، پاسخ ناقص و JSON نامعتبر به‌عنوان شکست گزارش می‌شود؛ تغییر خودکار به
سرویس پولی وجود ندارد. بررسی انسانی متن پیش از استفاده، برای اطمینان از
درستی سوابق لازم است؛ این مرحله فقط تولید پیش‌نویس است.

## مراحل بعدی

- منابع مجاز جستجو و استخراج آگهی، با ثبت لینک و تاریخ.
- فیلتر عنوان فنی، کشور و زبان انگلیسی؛ حقوق قابل مذاکره.
- بررسی جداگانهٔ شواهد حمایت از ویزا و کمک ریلوکیشن؛ موارد مبهم برای بررسی.
- ثبت پایدار آگهی، صف و سابقهٔ درخواست برای جلوگیری از ارسال تکراری.
- اجرای ساعتی و سقف قابل تنظیم؛ مقدار پیشنهادی اولیه پنج ارسال در روز.
- ارسال با ایمیل استخدامی مستند یا مسیر رسمی درخواست؛ بدون حدس آدرس ایمیل.

SEARCH_INTERVAL_SECONDS فاصلهٔ چرخه‌های جستجو در worker است.
DAILY_EMAIL_LIMIT و SEND_EMAILS در ماژول ارسال اعمال می‌شوند.

## ساختار ماژول‌ها

- app/settings.py: تنظیمات اتصال به مدل.
- app/sources.py: خواندن و اعتبارسنجی وایت‌لیست.
- app/intake.py: دریافت آگهی‌های نرمال‌شده از JSON.
- app/filtering.py: فیلتر اولیه و ارجاع شرایط مبهم به بررسی.
- app/llm.py: تولید پیش‌نویس با مدل انتخابی.
- app/storage.py: ثبت پایدار وضعیت و پیش‌نویس در SQLite.
- app/orchestrator.py: هماهنگی مراحل و سقف پیش‌نویس در هر اجرا.
- run_pipeline.py: نقطهٔ ورود خط لوله.
- config/sources.json: منابع و کشورهای هدف، قابل ویرایش.
- config/README.md: راهنمای افزودن سایت و سیاست مخاطب استخدام.

ارکستریتور فعلی یک خط لولهٔ قطعی پایتونی است؛ CrewAI هنوز وابستگی پروژه نیست.
بخش دریافت آگهی بعداً می‌تواند adapter یا Flow مربوط به CrewAI را فراخوانی کند.

### اجرای ارکستریتور

```bash
python source_config.py
python run_pipeline.py --jobs data/jobs.json
```

jobs.json آرایه‌ای از اشیاء شامل url، title، country، description،
english_working_language و وضعیت مستقل visa_sponsorship و relocation_support است.
برای هر وضعیت مثبت، فیلد متناظر با پسوند _evidence شامل quote و url لازم است.
این مرحله صحت ادعای مدرک را از اینترنت بازخوانی نمی‌کند؛ ورودی باید قبلاً بررسی
شده باشد. شروط مبهم review، خطای مدل pending و خروجی موفق drafted ثبت می‌شود.
موارد پردازش‌شده دوباره تولید نمی‌شوند. برای بازبینی تغییر آگهی، مدیریت نسخهٔ
آگهی و رابط بازگرداندن وضعیت هنوز نیاز به پیاده‌سازی دارد.

سقف پیش‌نویس --draft-limit فقط برای همان اجراست و سقف ارسال روزانه نیست.
قفل workerهای تولید پیش‌نویس هنوز پیاده نشده است؛ در ماژول مستقل ارسال،
رزرو تراکنشی و سقف روزانه اعمال می‌شوند.

## جستجوی اینترنتی و صف بررسی

```bash
python discover_jobs.py
python -m unittest discover -s tests -v
```

در .env مقدار BRAVE_SEARCH_API_KEY را تنظیم کنید. استفاده از سرویس جستجو
تابع حساب و هزینهٔ همان سرویس است؛ این برنامه کلید یا اشتراک تهیه نمی‌کند.
SEARCH_PROVIDER فعلاً brave است؛ adapter جستجو از سایر مراحل جداست.
SEARCH_MAX_QUERIES_PER_RUN و SEARCH_MAX_PAGES_PER_RUN مصرف هر اجرا را محدود می‌کنند.

برنامه برای هر منبع فعال، یک جستجوی محدود به دامنه با عنوان‌های فنی و عبارت‌های
visa/relocation می‌فرستد. سپس نتایج مجاز را می‌خواند. تمام مقصدهای redirect
پیش از دنبال شدن با وایت‌لیست مقایسه می‌شوند. اگر اطلاعات schema.org
JobPosting در HTML موجود باشد، عنوان، شرکت، کشور و شرح شغل استخراج می‌شود؛
سایر صفحه‌ها با برچسب unverified_page_candidate ذخیره می‌شوند و ممکن است
صفحهٔ فهرست باشند، نه یک آگهی واقعی. صفحات نیازمند JavaScript یا ورود
هنوز adapter مرورگر ندارند؛ دامنهٔ مجاز لزوماً به معنی پشتیبانی کامل سایت نیست.

همهٔ خروجی‌ها با وضعیت review در SQLite قرار می‌گیرند؛ وایت‌لیست، فهرست
دامنه‌های مجاز است و صف review، فهرست آگهی‌های نیازمند بررسی.
برنامه از روی وجود کلمهٔ visa یا relocation در نتیجهٔ جستجو، حمایت را
تأیید نمی‌کند و هیچ ایمیلی ارسال نمی‌شود. ادعای تناسب با رزومه نیز در مرحلهٔ
کشف صادر نمی‌شود. data/discovered_jobs.json فقط خروجی جدید همان اجراست.
موارد قبلی در دیتابیس می‌مانند؛ رابط تأیید و بازگرداندن review به pending
در مرحلهٔ بعد لازم است.

این مرحله با ابزار جستجو و استخراج قطعی پیاده شده، نه CrewAI.
CrewAI می‌تواند بعداً همین adapterها را به‌عنوان ابزار استفاده کند.
جستجو محدود و نمونه‌ای است، نه پیمایش کامل اینترنت؛ نتایج قدیمی و آگهی‌های
بسته نیز باید در بررسی بعدی کنار گذاشته شوند.

ماژول‌های جدید: web_search، web_fetch، job_parser و discovery؛
discover_jobs.py فقط نقطهٔ ورود است. تست‌ها بدون شبکه اجرا می‌شوند؛
اجرای واقعی با کلید Brave و مدل کاربر هنوز تست نشده است.

## ارسال ایمیل و تست

پیش‌فرض ارسال Gmail است؛ فقط این دو مقدار را در .env روی سرور وارد کنید:

```dotenv
SMTP_USERNAME=abdollahian61@gmail.com
SMTP_PASSWORD=YOUR_GOOGLE_APP_PASSWORD
```

سرور smtp.gmail.com، پورت 587 و STARTTLS خودکار انتخاب می‌شوند؛ فرستنده
همان SMTP_USERNAME است. رمز باید **App Password** گوگل باشد، نه رمز اصلی Gmail.
ابتدا تأیید دومرحله‌ای را فعال کنید و در
[App Passwords](https://myaccount.google.com/apppasswords) یک رمز برای Job Research بسازید.
فاصله‌های نمایشی App Password به‌صورت خودکار حذف می‌شوند. بعضی حساب‌های
سازمانی، دارای Advanced Protection یا تنظیمات خاص ممکن است این گزینه را نداشته باشند.

در .env.example مقدار SEND_EMAILS=true آماده است؛ فرمان send_draft.py واقعاً
ارسال می‌کند. برای dry-run آن را false کنید. اگر .env قدیمی دارید، مقدار
SEND_EMAILS=false قبلی را برای ارسال واقعی به true تغییر دهید؛ git pull فایل
.env شما را تغییر نمی‌دهد. worker هنوز فقط جستجو می‌کند و خودکار ایمیل نمی‌فرستد.

برای سرویس دیگری، SMTP_HOST، SMTP_PORT، SMTP_TLS_MODE و SMTP_FROM قابل
بازنویسی هستند. کلیدها و رمزها را در چت یا مخزن قرار ندهید.

```bash
python send_draft.py --draft data/draft.json --job-key test-001 --resume data/resume.pdf --test-to YOUR_OWN_EMAIL
python send_draft.py --draft data/draft.json --job-key STABLE_POSTING_KEY --resume data/resume.pdf --recipient data/recipient.json
```

برای تست، YOUR_OWN_EMAIL باید دقیقاً آدرس فرستنده باشد (پیش‌فرض: SMTP_USERNAME). draft.json دارای
subject و body است. resume.pdf رزومهٔ نهایی است؛ نمونهٔ رزومه ساخته نشده.
recipient.json باید شامل email، verified=true، purpose=job_application،
source_url و source_evidence حاوی ایمیل استخدامی منتشرشده باشد. دامنهٔ
source_url باید در وایت‌لیست باشد. این اطلاعات تأیید منبع از مرحلهٔ بررسی
وارد می‌شوند؛ ماژول SMTP به‌تنهایی صحت محتوا یا تناسب شغلی را بررسی نمی‌کند.
از این فرمان فقط برای پیش‌نویس‌ها و مقصدهای بررسی‌شده استفاده کنید.

کلید ثابت موقعیت برای جلوگیری از تکرار ضروری است؛ برای یک آگهی آن را عوض
نکنید. قبل از ارسال، رزرو در SQLite ثبت می‌شود. سقف روزانه به وقت تهران
است و شامل تلاش‌های رزروشده، تست و موارد نامطمئن نیز می‌شود. خطا یا قطع
ارتباط بعد از رزرو به uncertain می‌رود و خودکار دوباره ارسال نمی‌شود.
این روش از تکرار خودکار جلوگیری می‌کند، اما تحویل قطعی SMTP را تضمین
نمی‌کند؛ SMTP پذیرش پیام را نشان می‌دهد، نه رسیدن حتمی به صندوق مقصد.
وضعیت sending باقی‌مانده پس از crash نیز قبل از هر اقدامی باید بررسی شود.

برای تولید متن با OpenAI، LLM_BASE_URL=https://api.openai.com/v1،
LLM_API_KEY و نام مدل سازگار با Chat Completions حساب خودتان را تنظیم کنید.
با vLLM یا OpenRouter نیز تنظیمات موجود قابل استفاده‌اند.
API حساب OpenAI از اشتراک ChatGPT جداست. برنامه به این گفت‌وگو متصل نمی‌شود؛
رزومه و متن آگهی ورودی هر درخواست‌اند. برخی مدل‌ها پارامترهای متفاوت می‌خواهند
و ممکن است تنظیم adapter نیاز شود؛ بدون تعیین مدل، سازگاری زنده ادعا نمی‌شود.

تست‌های آفلاین، سقف روزانه بین اتصال‌های دیتابیس، جلوگیری از تکرار،
خطای نامطمئن، پیوست و dry-run را پوشش می‌دهند. هیچ ایمیل یا درخواست مدل
واقعی در این تست‌ها ارسال نشده است. استخراج خودکار ایمیل HR، بررسی
تناسب با CV و اتصال کامل صف بررسی به ارسال خودکار هنوز باقی است.

## نصب با Docker Compose

```bash
git clone https://github.com/abdollahian61/job_research.git
cd job_research
cp .env.example .env
mkdir -p inputs
# Copy your final PDF beside Dockerfile with the name resume.pdf
chmod 644 resume.pdf
docker compose build
```

.env را با کلید جستجو، آدرس مدل، SMTP و تلگرام تکمیل کنید. فایل‌های ورودی
مانند متن آگهی و recipient.json را در inputs بگذارید؛ رزومهٔ PDF کنار Dockerfile قرار می‌گیرد.
مدل vLLM سرویس جداگانهٔ شماست؛ این Compose مدل یا GPU را راه‌اندازی نمی‌کند.
LLM_BASE_URL باید از داخل کانتینر قابل دسترسی باشد؛ localhost به خود کانتینر
اشاره می‌کند، بنابراین IP یا DNS قابل دسترسی سرور مدل را وارد کنید.

```bash
docker compose up -d
docker compose logs -f --tail=100
docker compose run --rm job-research python discover_jobs.py
docker compose run --rm job-research python model_client.py --job inputs/job.txt
docker compose run --rm job-research python send_draft.py --draft inputs/draft.json --job-key test-001 --test-to YOUR_OWN_EMAIL
docker compose down
```

worker پیش‌فرض فقط کشف آگهی را تکرار می‌کند؛ بررسی، تولید و ارسال خودکار به
آن متصل نشده‌اند. فاصلهٔ چرخه‌ها از SEARCH_INTERVAL_SECONDS خوانده می‌شود.
حداقل فاصله ۶۰ ثانیه است و SEARCH_RUN_TIMEOUT_SECONDS زمان هر اجرا را
محدود می‌کند. قفل فایل از اجرای همزمان workerهای دارای volume مشترک جلوگیری
می‌کند؛ فرمان دستی discover_jobs.py خودش این قفل را نمی‌گیرد.
استفاده از --job-key ثابت و دیتابیس مشترک برای کنترل ارسال ضروری است.

دیتابیس و خروجی‌ها روی volume به نام job-data باقی می‌مانند؛ docker compose
down آن را حذف نمی‌کند. حذف volume باعث از دست رفتن سابقهٔ ضدتکرار می‌شود.
inputs و config فقط خواندنی mount می‌شوند؛ برای افزودن سایت sources.json را
روی میزبان ویرایش کنید. تصویر با کاربر غیر root اجرا می‌شود و کلیدها وارد
image نمی‌شوند. تنظیمات جدید .env با ساخت مجدد کانتینر اعمال می‌شوند.

## راه‌اندازی اعلان تلگرام

1. در Telegram، بات رسمی @BotFather را باز کنید و /newbot بزنید.
2. توکن را فقط در TELEGRAM_BOT_TOKEN داخل .env قرار دهید.
3. بات خودتان را باز کنید و /start بفرستید.
4. شناسهٔ چت خصوصی را بخوانید:
   `docker compose run --rm job-research python telegram_setup.py`
5. شناسهٔ خودتان را در TELEGRAM_CHAT_ID بگذارید و TELEGRAM_ENABLED=true کنید.
6. تست:
   `docker compose run --rm job-research python telegram_test.py`
7. سپس `docker compose up -d` بزنید.

اگر بات webhook فعال داشته باشد، getUpdates برای خواندن شناسه قابل استفاده
نیست؛ شناسهٔ چت را از تنظیمات همان بات تهیه کنید. در صورت چند شناسه، شناسهٔ
چت خصوصی خودتان را انتخاب کنید؛ برنامه حدس نمی‌زند.

اعلان‌ها شامل شروع/پایان عملیات، نتایج جستجو، ورود آگهی به صف، وضعیت
پیش‌نویس، نتیجهٔ ارسال و خطا هستند. متن رزومه و کلیدها در اعلان قرار نمی‌گیرند.
اگر تلگرام در دسترس نباشد، خطای اعلان در لاگ ثبت می‌شود و کار اصلی دوباره
اجرا نمی‌شود؛ اعلان فعلی صف تحویل و retry مستقل ندارد، پس تحویل همهٔ پیام‌ها
تضمین نمی‌شود. این قابلیت گزارش فعالیت است و دستور یا تأیید از تلگرام نمی‌گیرد.

تست‌های آفلاین با فرمان python -m unittest discover -s tests -v اجرا می‌شوند. این محیط Docker engine ندارد؛
build/run واقعی تصویر و اتصال زنده به Telegram، SMTP و سرویس مدل هنوز تست نشده‌اند.

## رزومهٔ PDF کنار Dockerfile

فایل نهایی خودتان را با نام ثابت **resume.pdf** در ریشهٔ پروژه، کنار
Dockerfile و docker-compose.yml قرار دهید. هیچ نسخهٔ رزومه‌ای در مخزن نیست.

- Compose فایل را فقط خواندنی به /app/resume.pdf وصل می‌کند؛ PDF داخل image کپی نمی‌شود.
- هنگام شروع worker، PDF بررسی می‌شود؛ فایل مفقود، نامعتبر، رمزدار یا بدون متن باعث توقف می‌شود.
- model_client.py و run_pipeline.py متن PDF را به مدل می‌دهند؛ profile.json دیگر الزامی نیست.
- send_draft.py همان PDF را پیوست می‌کند؛ --resume همچنان برای مسیر دلخواه قابل استفاده است.
- PDF باید متن قابل انتخاب، حداکثر ۱۰ MiB و حداکثر ۳۰ صفحه داشته باشد؛ OCR پشتیبانی نمی‌شود.
- محتوای رزومه در لاگ یا اعلان تلگرام نوشته نمی‌شود. برای تولید متن، به سرویس مدل تنظیم‌شده ارسال می‌شود.

نام یا مسیر فایل روی میزبان را در .env تغییر دهید، مثلاً:

```dotenv
RESUME_FILE=./Amir_Abdollahian_CV.pdf
```

RESUME_PATH برای اجرای مستقیم Python است و پیش‌فرض آن resume.pdf است.
در Compose مسیر داخلی همیشه /app/resume.pdf می‌ماند. فایل برای کاربر کانتینر
با UID 10001 باید قابل خواندن باشد. فایل‌های PDF و inputs از Git و build context حذف شده‌اند.

پس از جایگزینی رزومه یا تغییر مسیر، کانتینر را دوباره ایجاد کنید؛ rebuild لازم نیست:

```bash
docker compose up -d --force-recreate
```

بررسی رزومه در شروع worker، مسیر جستجو تا ارسال را خودکار نمی‌کند؛
worker فعلاً فقط کشف دوره‌ای آگهی را انجام می‌دهد. تولید پیش‌نویس و ارسال
با فرمان‌های جداگانهٔ بالا انجام می‌شوند.

## Gmail SMTP یا Gmail API؟

برای این پروژهٔ شخصی و صرفاً ارسال ایمیل، SMTP با App Password تنظیمات کمتری
دارد و نیازی به پروژهٔ Google Cloud ندارد. Gmail API هم از همان حساب Gmail
ارسال می‌کند، ولی به فعال‌سازی API، OAuth client و مدیریت توکن نیاز دارد؛
API key به‌تنهایی برای ارسال از حساب شخصی کافی نیست. OAuth برای دسترسی با
مجوزهای مشخص و توسعهٔ قابلیت‌های صندوق ایمیل انتخاب مناسب‌تری است؛ Google
در صورت امکان Sign in with Google را به App Password ترجیح می‌دهد.

راهنماهای رسمی:
- https://support.google.com/accounts/answer/185833
- https://developers.google.com/workspace/gmail/api/quickstart/python

در این تغییر تنها مسیر SMTP آماده شده؛ اتصال واقعی Gmail هنوز تست نشده است.
